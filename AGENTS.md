# AGENTS.md

## Project overview

This is the source repository for [git-scm.com](https://git-scm.com), the Git
project's homepage. It is a static site built with [Hugo](https://gohugo.io/)
(extended edition) and served via GitHub Pages. The default branch is
`gh-pages`.

## Repository structure

- `layouts/` — Hugo templates (`_default/baseof.html` is the main skeleton)
- `layouts/partials/` — Reusable template fragments (header, footer, sidebar,
  masthead, site-root for the homepage, book pages, etc.)
- `content/` — Page content (Markdown and HTML with Hugo front matter)
- `assets/sass/` — SCSS stylesheets, compiled by Hugo; `application.scss` is
  the entry point that imports all others
- `static/` — Static assets (images, JS) served as-is
- `data/` — Hugo data files (GUIs list, etc.)
- `external/` — Pre-rendered content sourced from other repositories (ProGit
  book, manual pages, translations); generated by scripts, do not edit directly
- `script/` — Helper scripts (local dev server, book/docs updaters, CI)
- `tests/` — Playwright test suite
- `hugo.yml` — Hugo configuration; also the source of truth for pinned
  versions (`hugo_version`, `pagefind_version`) and site params
  (`latest_version`, etc.)

## Sparse checkout

The repository is very large. Always use a sparse checkout for local
development. See the README for the minimal sparse checkout needed to build and
test the site. Many contributors will never need the `external/` tree.

## Building the site

```sh
hugo                  # build into public/
```

On Windows, some filenames contain question marks, which are forbidden on
Windows filesystems. Before building, run the workaround from the README to
strip `?` from `url:` front-matter attributes and mark those files as
`--assume-unchanged`.

## Pagefind (client-side search index)

[Pagefind](https://pagefind.app/) generates the search index that powers the
site's client-side search. It runs as a separate step after Hugo:

```sh
npx -y pagefind@$(sed -n 's/^ *pagefind_version: //p' <./hugo.yml) --site public
```

The pinned Pagefind version is stored in `hugo.yml` under `pagefind_version`.

**Important:** The Pagefind indexing step is significantly more expensive than
the Hugo build itself (roughly 7× slower) and also prevents Hugo's live-reload
from working. Only run it when you actually need the search functionality — for
example, when debugging or testing the search feature. For all other work
(layout, styling, content, non-search tests), a plain `hugo` build is
sufficient and much faster.

## Local development server

```sh
node script/serve-public.js
```

This starts a server on http://localhost:5000/ that serves `public/` with no
caching — files are read from disk on every request. There is no need to
restart it after rebuilding with Hugo.

For Hugo's built-in live-reload server (different URL scheme):

```sh
HUGO_UGLYURLS=false hugo serve -w
```

## Generated data files

Files under `external/` are generated by scheduled GitHub Actions workflows
and are not meant to be edited by hand. The workflows call Ruby scripts from
`script/`:

- `.github/workflows/update-git-version-and-manual-pages.yml` runs
  `script/update-docs.rb` to generate `external/docs/data/docs.json` and the
  English manual page content under `external/docs/content/`.
- `.github/workflows/update-translated-manual-pages.yml` also runs
  `script/update-docs.rb` (with the `l10n` argument) to generate the
  translated manual pages.
- `.github/workflows/update-book.yml` runs `script/update-book2.rb` to
  generate `external/book/data/book/<lang>.yml` and the book content under
  `external/book/content/book/`.

The scripts can be run locally for debugging (see the README), but in normal
operation they are only invoked by these workflows.

If the generated output is wrong, fix the script, not the generated file.

**Book data/content coupling:** Hugo's templates assume that every book content
page has a corresponding data file (`external/book/data/book/<lang>.yml`). If
a sparse checkout or CI configuration includes `external/book/content/book/`
without also including `external/book/data/book/`, the build will fail with a
`reflect: call of reflect.Value.Type on zero Value` error from
`chapters.html`.

**YAML caveat:** Hugo v0.155.3+ uses go-yaml v3, which counts structurally
identical non-scalar nodes (maps, sequences) as implicit aliases even when the
file contains no explicit YAML anchors. The hard limit is 10,000 such nodes
across the entire file. The `docs` data file was switched from YAML to JSON
(`docs.json`) to sidestep this limit, since Hugo supports JSON data files
natively. If you add new data-generation scripts that produce large repetitive
data sets, prefer JSON over YAML to avoid hitting this limit.

## CSS / styling

Stylesheets live in `assets/sass/`. Key files:

- `variables.scss` — breakpoints (`$default: 940px`, `$mobile-m: 640px`, etc.),
  font families, base sizing
- `layout.scss` — page skeleton (`.inner`, `header`, `aside`, `#content`,
  `#content-wrapper`, `#masthead`, `footer`, responsive breakpoints)
- `front-page.scss` — homepage-specific layout (`#front-content`,
  `#front-navigation`, `#front-downloads`)
- `dark-mode.scss` — CSS custom properties for dark/light themes

The homepage uses a different layout from all other pages (masthead +
site-root partial, no sidebar). Non-homepage pages use `#content-wrapper`
(flexbox) with a sidebar (`aside`) and a `#content` area.

When making layout changes, verify visual alignment across the homepage,
content pages (e.g. `/about`), documentation pages, and book pages. The
Playwright test suite includes an alignment check for this.

## Testing

The test suite uses [Playwright](https://playwright.dev/) and lives in
`tests/git-scm.spec.js`, configured via `playwright.config.js`.

```sh
# Install Playwright and at least one browser
npm install @playwright/test
npx playwright install chromium    # or firefox, webkit, chrome

# Run tests against the local server
PLAYWRIGHT_TEST_URL='http://localhost:5000/' npx playwright test --project=chromium

# Run a single test by name
PLAYWRIGHT_TEST_URL='http://localhost:5000/' npx playwright test -g "<test name>" --project=chromium
```

When `PLAYWRIGHT_TEST_URL` is set to `http://localhost:5000/`, the Playwright
config automatically starts `node script/serve-public.js` as a web server
(reusing an existing one if already running).

On Windows, tests use a 60-second timeout (vs the default 30 seconds).

## Commit message conventions

- No bullet points; use flowing prose.
- Focus on context, intent, and justification — not what is obvious from the
  diff.
- Reference related commits with their abbreviated SHA and subject line, e.g.
  `9f2a5aeb9 ("Continue to display sidebar when page scrolls")`.
- Trailers in this order: `Assisted-by:` (if applicable), then `Signed-off-by:`.
  Use `--trailer` flags (not `-s`) to control ordering.

## PowerShell / Windows notes

- Use PowerShell syntax, not Bash. Do not chain commands with `&&`.
- Use `-Replace` instead of `sed` for string substitution.
- WSL is available for running Ruby and Bash scripts that don't work natively
  on Windows.
- Some content files have colons or question marks in filenames that are
  incompatible with Windows filesystems; the README documents workarounds.
